## Context

当前启动流程在 `lifecycle.rs` 中直接创建统计采集器、桌宠窗口、快捷面板和托盘，并通过静态 Tauri command 把具体 Rust 状态暴露给前端。`pet_window.rs` 还同时拥有 Win32 窗口线程、动画帧、透明命中、尺寸和皮肤切换；`pet_skins.rs` 使用编译期内嵌资源清单；`QuickPanel.svelte` 直接维护统计、大小和皮肤设置的界面状态。

这个现状适合单体首版，但不适合用户逐步安装能力。Tauri 的 command 注册是编译期的，Svelte 的界面资源也随应用构建，不能把任意用户脚本直接当作动态插件加载。Windows 桌宠还要求启动快、常驻资源少，并且不能让第三方资源接触 HWND、GDI 或统计数据库。

本设计借鉴 DeepSeek Harness 的 capability seam、profile/bundle 组合和可撤销注册思想，但不引入完整 Cordis，也不把任意代码执行作为首版插件模型。详细用户行为以 proposal 和三个 capability spec 为准。

## Goals / Non-Goals

**Goals:**

- 在核心宿主和可安装插件之间建立一个小而稳定的接口，让新增皮肤或面板能力不再修改 Win32 窗口实现。
- 让官方插件和本地导入插件使用同一套 manifest、状态和贡献生命周期。
- 首次启动只登记并启用 `simple-cloud` 皮肤；快捷面板、使用统计和大小设置作为预装官方插件继续提供当前体验；其他皮肤只作为可安装目录条目。
- 让安装、启用、禁用、卸载和启动恢复具有原子性、可测试性和明确故障回退。
- 只加载当前皮肤的原生帧，按需创建插件管理界面，保持桌宠常驻 CPU、内存和窗口数量稳定。
- 为未来 Bun/TypeScript SDK 提供可复用的协议类型和校验规则，但首版不需要动态脚本运行时。

**Non-Goals:**

- 不克隆 Cordis 的通用服务树、事件 DSL 或热重载系统。
- 不允许插件在宿主进程内执行任意 JavaScript、Rust DLL、进程、网络请求或 Windows API。
- 不在本次设计中解决在线目录、账号、支付、签名更新、插件依赖解析或 WASM/sidecar 运行时。
- 不改写使用统计的采集口径、隐私范围或 SQLite 汇总模型。

## Decisions

### 1. 采用“协议、宿主、SDK”三层，而不是 SDK 先行

插件协议是兼容性的来源，描述 manifest、贡献类型、权限和宿主 API 版本；插件宿主负责校验、安装、激活和撤销；Bun/TypeScript SDK 以后只负责类型、模板、资源检查和 `.petpack` 打包。这样没有 SDK 的资源作者也可以发布声明式皮肤包，SDK 也不会把核心实现细节暴露给插件作者。

考虑过的替代方案：

- **只做 SDK**：无法定义安装状态、权限和故障恢复，插件作者会直接依赖当前 Rust/Svelte 实现，协议很快失稳。
- **直接使用 Tauri plugin API**：Tauri 插件适合随应用编译的 Rust/JavaScript 扩展，不适合作为终端用户可安装的资源包；它也不能在运行时增加新的 command。
- **直接加载 WebView JavaScript**：会让未信任代码进入具有 Tauri IPC 的页面，且任意 Svelte 组件不能安全地从已安装目录动态导入。

### 2. 用显式的深模块作为宿主接缝

宿主内部划分为几个对调用者保持小接口的模块：

```text
PluginManager
  ├── PluginRegistry       查询和持久化状态
  ├── PluginInstaller      校验、暂存、原子提交和卸载
  ├── PluginRuntime        启用、撤销和故障隔离
  └── ContributionRegistry 皮肤、面板、设置和菜单贡献

Core Host
  ├── PetCapability        显示、尺寸、位置和皮肤资源交换
  ├── PanelCapability      声明式卡片、设置区块和固定动作
  ├── StorageCapability    插件命名空间存储
  └── PermissionCapability 权限声明和确认
```

`lifecycle.rs` 只负责组装宿主和官方插件，不再知道每个皮肤或统计功能的细节；`pet_window.rs` 保持 Win32 实现，只接受经过校验的资源引用和有限的桌宠操作。内置官方插件与本地 `.petpack` 是两个真实的资源适配器，因此这条接缝有实际变化，不是为假想的第三种实现提前抽象。

### 3. 首版使用声明式 `.petpack`，不执行插件代码

`.petpack` 是 ZIP 容器，根目录必须有严格 JSON manifest；资源路径只能指向包内文件。manifest 至少包含：`manifestVersion`、稳定 `id`、`version`、中文名称、`kind`、`hostApi`、`permissions` 和 `contributes`。贡献 ID 使用插件 ID 命名空间，避免不同作者冲突。

首版允许的贡献类型是：

- `skins`：透明 RGBA 主资源、缩略图、基准尺寸和统一待机帧参数。
- `panelCards`：由宿主渲染器支持的文本、数值、列表和固定动作卡片。
- `settings`：宿主支持的滑块、开关和选项描述。
- `menus`：调用已批准宿主动作的菜单项。

未知贡献类型、任意脚本入口和未支持权限在加载时拒绝。未来若引入逻辑插件，将另建进程或 WASM 协议，不改变声明式包的信任模型。

### 4. 用本地注册表和版本目录管理安装状态

插件文件放在应用本地数据目录下的版本目录，例如：

```text
<app-local-data>/plugins/<plugin-id>/<version>/
<app-local-data>/plugin-registry.json
<app-local-data>/plugin-data/<plugin-id>/
```

注册表版本 1 记录插件 ID、版本、来源、内容校验值、状态、权限确认和最后一次可展示的错误。安装目录是资源事实来源，注册表是启用状态事实来源；仅出现在目录中的未知文件不会自动加载。

选择 JSON 而不是新增插件 SQLite 数据库，是因为首版只有单用户、少量插件和简单状态迁移；现有 SQLite 继续只负责使用统计，避免插件卸载与统计数据事务互相耦合。注册表写入沿用现有偏好的临时文件、同步和 Windows 原子替换策略。未来出现依赖图、版本回滚或多配置文件时再评估 SQLite，不在本次引入。

### 5. 安装先暂存，启用再提交贡献

安装流程先在临时目录解压并限制压缩展开大小、路径、图片尺寸和总文件数，完成 manifest 与资源校验后原子移动到版本目录，再原子更新注册表。安装成功不等于启用成功；启用阶段重新解析贡献并在全部成功后一次性登记。任何阶段失败都删除临时文件，保留旧版本和旧贡献。

插件启用产生的注册动作必须返回可撤销的句柄；禁用、卸载或部分失败时按相反顺序撤销。这借鉴 Harness 的可逆 effect，但只在各个明确的贡献注册表中实现，不建立全局事件魔法。

### 6. 官方插件通过 bootstrap 进入初始 profile

首次启动时，bootstrap 注册核心宿主、插件管理器、快捷面板、使用统计、大小设置和 `simple-cloud` 皮肤。前三类官方能力可以是受信任的原生适配器，但仍通过 `PluginRuntime` 注册自己的贡献；只有 `simple-cloud` 皮肤资源进入初始已安装清单。橙色小龙、三花猫和未来皮肤只进入本地官方目录的元数据，用户安装前不进入可用贡献集合。

核心仍保留一份最小默认皮肤回退资源，以防注册表或默认插件资源不可用。它不作为可卸载插件暴露，也不与用户选择历史混合；正常情况下桌宠使用已安装的 `simple-cloud` 贡献。

现有 `pet-skin-preferences.json` 和 `pet-preferences.json` 不直接删除。启动时先读取插件状态，再把旧皮肤偏好映射到已安装贡献；无法映射时使用 `simple-cloud`。迁移完成后，新选择由插件命名空间保存，旧文件保留兼容读取窗口。

### 7. 用通用 Tauri IPC 和声明式面板渲染器连接前端

Tauri 只注册固定的宿主命令，例如查询插件、导入包、启用、禁用、卸载、读取贡献和执行固定动作。前端传递的是插件 ID、贡献 ID 和动作 ID，不传递模块路径、脚本、URL 或 HWND。这样动态插件不会绕过编译期 command 表。

快捷面板拆成宿主 shell 和声明式贡献渲染器：统计摘要、皮肤画廊和大小控制先迁移为官方贡献；插件包只能使用已支持的渲染类型，不能注入任意 Svelte 组件。插件管理界面按需创建，关闭时释放缩略图和临时状态，不增加常驻 WebView。

### 8. 资源和故障预算优先于扩展数量

启动时只读取注册表和 manifest，不解码所有皮肤；设置或插件目录打开时才读取缩略图，切换皮肤时在桌宠线程中构建候选帧和 GDI surface，成功后一次交换。任意时刻只保留当前帧和候选帧，避免按已安装皮肤数量线性增加常驻内存。资源尺寸、展开大小和缩略图限制由协议固定，不能由插件自行放宽。

### 9. SDK 作为协议的外部工具

后续 Bun SDK 包含 manifest 类型、资源检查器、创建模板、打包器和本地验证命令；它输出宿主已经支持的声明式包，不负责启动桌宠或提供隐藏权限。SDK 版本与 `hostApi` 解耦：插件包声明宿主兼容范围，SDK 可以独立更新。首版只在协议层预留这些字段，不把 SDK 加入桌宠运行时依赖。

## Risks / Trade-offs

- **[插件协议过早固定]** → 只冻结 manifest 版本、贡献类型和宿主能力 ID；未知字段和贡献明确拒绝，后续通过 `manifestVersion`/`hostApi` 增量演进。
- **[用户导入恶意或超大压缩包]** → 导入前限制路径、文件数、压缩展开总量和图片解码尺寸；资源插件不执行代码，安装目录只接受原子提交后的文件。
- **[插件故障导致桌宠失去外观]** → 核心保留不可卸载的默认回退资源；启用采用候选贡献交换，失败时保留上一套已提交皮肤。
- **[官方插件与第三方插件行为不一致]** → 官方插件也必须通过同一套贡献注册和状态查询；受信任原生适配器只存在于宿主内部，不改变对外 manifest。
- **[声明式面板能力不足]** → 首版只覆盖统计摘要、文本、数值、列表、设置控件和固定动作；需要任意布局或逻辑时另行设计沙箱插件，不偷偷扩大首版权限。
- **[安装包增加资源体积]** → 首次发布只随核心携带默认皮肤和目录元数据，其他官方皮肤按需导入；桌宠常驻路径只保留当前皮肤帧。
- **[旧皮肤变更与新默认策略冲突]** → 在实现前先把尚未归档的皮肤变更中的“三套默认可选”要求与本设计合并为“默认一套、其余目录可安装”，不直接删除旧偏好文件或旧资源。

## Migration Plan

1. 先完成协议类型、manifest 校验、注册表读写和纯 Rust 测试，不改变现有桌宠启动行为。
2. 把当前静态皮肤清单包成内置资源适配器，新增 `simple-cloud` bootstrap 和核心回退；保留旧皮肤偏好的兼容读取。
3. 建立插件运行时与通用 Tauri IPC，将统计、快捷面板、大小设置和默认皮肤注册为官方插件，确认重复启用不会创建第二个采集器、面板或窗口。
4. 将快捷面板的皮肤、大小和统计入口改为宿主贡献渲染，加入中文插件目录和本地 `.petpack` 导入；目录中显示其他官方皮肤但不把它们登记为已安装。
5. 在 Windows 10/11 x64 上验证首次启动、离线目录、安装失败回滚、启用/禁用、默认皮肤保护、DPI/大小/位置、锁屏恢复和旧偏好迁移，并记录常驻资源占用。

回滚时保留旧的偏好文件、统计数据库和内置默认资源；如果插件注册表或宿主初始化失败，应用降级到核心桌宠和受信任的官方适配器，不删除用户数据。确认新运行时稳定后，再移除旧的静态三皮肤装配路径。

## Persistence and Recovery

- `plugin-registry.json` 保存注册表版本、插件版本、来源、校验值、状态、权限确认和最后错误；采用严格 JSON 与原子替换。
- `<app-local-data>/plugins/<id>/<version>` 保存已提交的包内容；临时安装目录不参与启动发现。
- `<app-local-data>/plugin-data/<id>` 保存插件独立设置；禁用不删除设置，卸载是否清理设置由管理界面明确确认。
- 核心 `pet-preferences.json`、旧 `pet-skin-preferences.json` 和 `daily-usage.sqlite3` 保持原格式，迁移失败时按旧格式读取并使用 `simple-cloud` 回退。
- 启动顺序为：读取并校验注册表 → 恢复核心与官方 bootstrap → 加载已启用贡献 → 记录失败插件并继续 → 创建桌宠窗口和按需面板。
