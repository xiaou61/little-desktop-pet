## Context

仓库当前没有根级 README；应用代码已经具备 Windows 透明桌宠、点击快捷面板、大小设置、使用统计和皮肤资源，但插件宿主变更仍处于开发中。现有包名、Tauri 配置和 OpenSpec 状态可以作为命令和状态的事实来源；`output/` 下的截图来自验证过程，不适合作为长期稳定的文档资产路径。

本设计参考了 DeepSeek Harness 的“项目定位 → 运行 → 开发/社区”顺序、Tauri 的“介绍 → 快速开始 → 特性 → 平台”顺序、PowerToys 的“功能 → 安装 → 更新 → 路线图”顺序，以及 `bat` 对“使用 → 安装 → 定制”的分层方式。README 会吸收这些信息架构，不复制其徽章、宣传语或与本项目无关的章节。

## Goals / Non-Goals

**Goals:**

- 让第一次打开仓库的人在首屏知道“小桌宠”是 Windows 桌面宠物，而不是单纯的软件使用统计工具。
- 用真实桌宠媒体和简短文字凸显主体验，再用一个清晰章节解释“核心宿主 + 官方插件 + 可安装插件包”的长期方向。
- 让“已实现、开发中、规划中”在 README 中有统一且可扫描的表达，并能链接到对应 OpenSpec 变更。
- 让用户可以复制命令运行项目，开发者可以找到项目结构、测试、构建、隐私和资源授权说明。
- 保持 README 在 GitHub、代码镜像和纯文本环境中都能阅读，不依赖动态服务或在线目录。

**Non-Goals:**

- 不在 README 中设计新的产品行为或替代 OpenSpec 的详细需求与任务。
- 不把插件基础设施尚未完成的内容写成可下载、可安装或已验证的功能。
- 不在首版 README 中维护实时数据、下载量、版本徽章、CI 徽章或第三方服务状态。
- 不将临时测试输出、带个人桌面信息的截图或未获授权的参考素材复制到文档资产。

## Decisions

### 1. 根 README 使用中文优先的单页结构

README 采用中文正文，保留命令、路径、协议字段和产品/项目名的原文；首屏结构固定为：

1. 产品名和一句话定位。
2. 桌宠本体或点击后快捷面板的真实截图/动图。
3. 当前可用能力的短列表。
4. 可插件化架构摘要和状态表。
5. 快速开始。
6. 隐私、项目结构、开发检查、路线图、资源授权与贡献入口。

选择单页而不是拆成多份首页文档，是因为项目仍处于早期，用户首先需要一条从认识产品到运行项目的短路径。详细插件协议继续放在 OpenSpec 和未来 SDK 文档中，README 只提供稳定入口。

### 2. 用“能力状态表”表达插件化，而不是用营销口号

README 使用统一的状态标签：

| 状态 | 含义 | README 允许的表述 |
| --- | --- | --- |
| 已实现 | 当前代码和验证可以支持 | “现在可以……” |
| 开发中 | 已有 OpenSpec 或部分代码，但还没有完成验收 | “正在构建……” |
| 规划中 | 已明确方向但尚未进入实现 | “计划支持……” |

插件宿主、`.petpack` 安装、启用/禁用和 SDK 在 `add-plugin-system-foundation` 完成前必须标记为“开发中”，不能放在“立即可用”列表。当前默认皮肤和已有统计/快捷面板功能按实际代码状态描述；“默认只有 `simple-cloud`、其他皮肤从目录安装”作为目标策略链接到插件变更，而不是伪装成已完成行为。

这样既能凸显产品的可插件化方向，又不会让 README 失去可信度。每个“开发中”条目至少链接到一个 OpenSpec 变更或代码入口，方便状态更新。

### 3. 插件架构使用兼容性最好的文本图和表格

核心架构使用 fenced code block 展示，避免 Mermaid 在不同 README 渲染器上表现不一致：

```text
小桌宠 Core Host
  ├─ 桌宠窗口与基础交互
  ├─ 插件管理器
  ├─ 本地存储与权限
  └─ 通用宿主接口
       ├─ 官方预设插件：统计 / 快捷面板 / 大小设置 / 默认皮肤
       └─ 用户安装插件：皮肤 / 动画 / 面板卡片 / 未来能力
```

旁边的状态表说明当前边界：核心桌宠是首要体验，插件系统是开发中的扩展方向；首版资源插件不执行任意代码，在线商店和 WASM/sidecar 属于更后续的路线图。图和表格只描述稳定概念，不嵌入会随实现变化的 Rust 模块名。

### 4. 截图和动图使用稳定的文档资产目录

新建 `docs/assets/readme/` 作为 README 专用媒体目录，至少准备桌宠本体、点击后的玻璃快捷面板和完整统计三张压缩 PNG；如果录制动图，限制在短时长和小尺寸，并提供同一场景的静态 PNG 回退。README 使用相对路径和中文替代文本，不引用 `output/`、临时目录或本机绝对路径。

截图必须在干净测试数据和无个人窗口的桌面上生成；不得出现 Windows 用户名、文件路径、窗口标题、应用使用明细、账号、令牌或未获授权的第三方角色。媒体尺寸在任务验收时固定，防止 README 首屏因高分辨率图片跳动或过度占用仓库。

### 5. 快速开始只记录仓库当前可验证命令

快速开始按“环境 → 安装 → 开发 → 检查 → 构建”组织，并从当前 `package.json`、`Cargo.toml` 和 Tauri 配置核对：

```text
环境：Windows 10/11 x64、Bun、Rust 工具链、WebView2
安装：bun install
开发：bun run tauri:dev
检查：bun run check / bun test
构建：bun run build / bun run tauri:build
```

README 不写未经验证的发布安装器 URL、云服务配置、在线插件下载命令或 Linux/macOS 支持。若某个命令因环境限制暂时不能验证，任务中必须标记为待确认，而不是在 README 中猜测。

### 6. 隐私和资源授权各保留一个事实来源

README 只摘要说明：统计数据本地保存、不收集窗口标题/文档名/键盘内容/截图/网络活动、不发送遥测；详细皮肤来源和授权继续链接到 `src-tauri/assets/README.md`。不在 README 复制长版权说明或临时参考仓库清单，避免出现两个互相漂移的授权事实来源。

### 7. 用内容核验清单保证 README 不会陈旧

实现 README 时增加一个文档检查清单，逐项核对：

- 文件路径和命令确实存在。
- 当前能力状态与 OpenSpec、应用代码和验证结果一致。
- 插件系统未完成时，所有相关内容仍带“开发中”标签。
- 图片文件存在、尺寸稳定、替代文本存在且不泄露隐私。
- 链接目标存在，未添加不存在的许可证、发布页或贡献指南。
- README 中的技术栈版本和平台范围与 `package.json`、`Cargo.toml`、Tauri 配置一致。

README 变更不需要新的运行时数据迁移；如果截图、链接或命令核验失败，回滚只需移除不正确的文档内容和媒体资产，不触碰应用数据。

## Risks / Trade-offs

- **[插件愿景被误读为当前功能]** → 首屏使用状态表和 OpenSpec 链接，所有未完成条目明确标记“开发中/规划中”。
- **[README 过于像营销页而不像开发项目首页]** → 只保留一张主视觉和一段定位，后续优先放运行命令、隐私、结构和验证信息。
- **[截图包含敏感信息或第三方素材]** → 使用干净测试数据、固定截图流程和专用资产目录，发布前人工检查媒体。
- **[命令随项目演进而失效]** → 任务中从实际配置核验命令，并把 README 核验列入后续变更的文档检查。
- **[维护成本随状态表增长]** → 只维护少量高层能力状态，详细进度由 OpenSpec 变更负责，README 不复制任务清单。

## Migration Plan

1. 创建稳定的 README 媒体目录并生成无敏感信息的三张当前界面截图。
2. 按本设计的结构新增根级 `README.md`，先写当前事实、隐私、运行命令和项目结构。
3. 加入插件化架构摘要、状态表和 `add-plugin-system-foundation` 链接，明确默认皮肤策略仍处于开发中。
4. 校验所有路径、命令、图片替代文本、链接和资源授权入口，运行 Markdown 链接/格式检查。
5. 通过审阅后再将 README 作为后续插件实现和发布变更的文档入口；插件系统完成阶段只更新状态与链接，不重写整体结构。

文档变更失败时可以直接回退新增 README 和 `docs/assets/readme/`，不会影响 Rust、前端、数据库或用户本地数据。
